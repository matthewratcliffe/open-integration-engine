# FHIR Connector — OIE engine extension

A FHIR **source** connector that presents a RESTful facade in front of a channel and
answers it with what the channel's destinations return, and a FHIR **destination**
connector that performs one FHIR interaction against a remote server. Both speak **R4 and
R5**, selected per connector.

**Status: built, installed, and exercised end to end on this stack.** Channels using both
connectors deployed on the running engine, served live requests, and returned correct FHIR
responses — see [Verified](#verified) for the transcript. The FHIR *payloads* are the
channel's business: nothing here validates a resource against a profile or converts between
releases.

## What each half does

**FHIR Listener (source).** Binds a port, parses the FHIR URL grammar, and hands the
channel the request plus everything it worked out about it. When the destinations are done
it builds the HTTP response: status code, `Location`, `ETag`, `Last-Modified`, a media type
carrying the right `fhirVersion`, and an OperationOutcome whenever there is nothing else
valid to send.

**FHIR Sender (destination).** Sends one interaction per message — create, update, patch,
read, vread, search, delete, history, transaction or `$operation` — with authentication,
conditional headers and `Prefer`. The response body becomes the destination's response, so
a facade in front of the same channel can return it verbatim; the status line, headers,
`Location`, `ETag` and the id the server assigned go into the connector map.

## Design

| Decision | Choice | Why |
| --- | --- | --- |
| FHIR model library | **None** | Two releases of HAPI's structure jars are well over a hundred megabytes loaded into the engine's JVM, to do a job this connector does not do: the resources pass through untouched. What the connector *must* read — `resourceType`, `id`, `meta.versionId`, `meta.lastUpdated`, `Bundle.type` — it reads with Jackson (JSON) or a DOM parse with entity resolution off (XML). |
| R4 and R5 | One enum, not two code paths | At the RESTful layer the releases differ in exactly two things: the `fhirVersion` media type parameter (`4.0` / `5.0`) and `CapabilityStatement.fhirVersion` (`4.0.1` / `5.0.0`). The two resources this connector generates — OperationOutcome and CapabilityStatement — are structurally identical in both for the elements used. Adding R4B is a line in `FhirVersion` and a line in each settings panel. |
| Third-party jars | **None bundled** | Jetty (the listener's socket), Apache HttpClient (the sender) and Jackson are already in the engine's `server-lib` and visible to an extension classloader — the same way the core HTTP connector uses Jetty without shipping it. |
| TLS | Either end of the wire | Off by default, and the socket is plain HTTP for something in front to terminate — this stack's nginx overlay does exactly that (`:8444` → `engine:8081`), and `X-Forwarded-Proto`, `-Host` and `-Prefix` are honoured when building the advertised base URL. Turn **Serve TLS** on and the listener presents the certificate itself, with optional client certificates. See [TLS](#tls). |
| Unroutable requests | Answered by the connector, not the channel | `GET /favicon.ico` should not wake a channel up. The URL grammar is parsed exactly, and each rejection carries the distinction a client needs: **404** for a URL that names nothing, **405** for one that exists but not with that method, **406** for content negotiation, **413** over the size limit, **503** when the channel is stopped. |
| `GET [base]/metadata` | Generated by the connector by default | A facade has to answer it before the channel author has written anything, and the connector knows which interactions and resource types are enabled. It does **not** know the channel's search parameters or operations, so it claims none. Four modes: generate, serve a custom statement, pass it to the channel, or 404. |
| Response status code | Derived, overridable | 201 for a create, 204 for a body-less delete, 202 when the message is queued, 500 on error, 200 otherwise — with a `responseStatusCode` property (supporting `${}`) for a channel that needs a different answer. |
| Non-FHIR responses | Wrapped in an OperationOutcome | A destination that returns plain text, or an error string, would otherwise break the facade's contract. On by default; turn it off to pass bodies through untouched. |
| JSON ↔ XML | Never converted | With no FHIR model there is no honest conversion, so a channel's response is sent as whatever it actually is (sniffed from the first character) rather than as whatever the client asked for. Only connector-generated bodies honour `Accept`/`_format`. |
| Response for a create | `Location` from the returned resource | The connector cannot invent an id; a create whose channel returns an empty body gets no `Location`, which is better than a fabricated one. `ETag` is weak (`W/"2"`), because a FHIR version id identifies the version of a resource, not a serialisation of it. |
| Default Response setting | `Auto-generate (Destinations completed)` | A facade whose purpose is to return what a destination produced must not answer before the destinations have run. The default yields a correct empty success; returning the resource is one more step — select that destination by name in **Response**. |
| Batching | Off, and not offered | A FHIR request carries one resource or one Bundle. Splitting a transaction Bundle at the source could never produce the single matching response Bundle a transaction must return. |
| Service plugin | Ships alongside the connectors | The engine deserialises channel XML through an XStream that permits nothing by default. Without registering these two properties classes, every channel using the connector would load as "This channel is invalid. Verify all required extensions are loaded correctly" — with the extension loaded perfectly well. The plugin registers them at server start. Same shape as the core TCP connector's "required for correct use of the TCP connectors" plugin. See [below](#why-there-is-a-service-plugin). |
| Web console panels | Written against `platform` alone, importing nothing | The console's own connector panels `import { ConnectorForm } from '/connectors/react-forms.js'`, which resolves through the page's import map. That works for panels shipped *inside* the web administrator's WAR and fails for one served by the engine: the module is imported from a base the browser will not resolve a rooted specifier against, so the import throws and the plugin never registers -- and a connector with no registered panel silently reads "(no web editor)". These panels take the host's React instance and code-editor factory off the `platform` object handed to `register()`, and reimplement the form layer against the console's own CSS classes. |
| Package | `org.openintegrationengine.connectors.fhir` | Naming the classes `com.mirth.connect.connectors.fhir` would have been covered by the engine's built-in allowlist for free, and a good deal of third-party Mirth code does exactly that. A package is a claim about who maintains the code, it is baked into every channel that ever uses the connector, and three lines of registration is a small price for not making that claim falsely. |

## The URL grammar

Parsed exactly as R4/R5 §3.1.0.1 defines it, relative to the configured base path:

```
[base]                                 search-system / transaction / batch / capabilities (OPTIONS)
[base]/metadata                        capabilities
[base]/_history                        history-system
[base]/$op                             operation (system)
[base]/[type]                          search-type / create / conditional update|patch|delete
[base]/[type]/_history                 history-type
[base]/[type]/_search                  search-type (POSTed form, merged into parameters)
[base]/[type]/$op                      operation (type)
[base]/[type]/[id]                     read / update / patch / delete
[base]/[type]/[id]/_history            history-instance
[base]/[type]/[id]/_history/[vid]      vread
[base]/[type]/[id]/$op                 operation (instance)
[base]/[type]/[id]/[compartment-type]  compartment search
```

`POST [base]` is a transaction or a batch depending on `Bundle.type`, which the connector
reads from the body before deciding.

## TLS

Off by default: the listener is plain HTTP and something in front terminates TLS.
That is the right shape when there is a proxy anyway — private keys stay out of
the engine, renewal is somebody else's reload, and `X-Forwarded-Proto` already
makes the advertised base URL come out right.

Turn **Serve TLS** on when there is no proxy to put in front, when the hop between
proxy and engine crosses anything you would not shout across, or when a partner
requires client certificates that the *application* checks rather than something
upstream that strips them.

| Setting | |
| --- | --- |
| Serve TLS | HTTPS on this port instead of HTTP |
| Key Store File | the store holding the server certificate and its private key. A relative path is taken from the engine's application data directory — the volume this stack persists, so a certificate survives a rebuilt container |
| Key Store Password | channel XML is not an encrypted store: use `${configurationMapKey}` or a Key Store plugin secret |
| Key Store Type | `PKCS12` (the JDK's own default, and what openssl and certbot produce) or `JKS` |
| Key Alias | which certificate to present. **Required** when the store holds more than one private key — the channel refuses to deploy rather than serving whichever one sorted first |
| Key Password | the key's own password, when it differs from the store's |
| Client Certificates | `NONE`, `WANT` (ask, accept either way) or `NEED` (refuse without a valid one) |
| Trust Store File | what client certificates are verified against. **Required** for `WANT` and `NEED` |
| Protocols | `TLSv1.2,TLSv1.3` by default. Blank leaves the JDK's list, which on some builds still includes TLS 1.0 and 1.1 |
| Cipher Suites | blank uses Jetty's defaults, which already exclude the suites with known problems |

**The trust store is not optional for client authentication.** Without one the JDK
falls back to its bundled CA list, so "client certificate required" would be
satisfied by a certificate from any public CA on earth — mutual TLS that verifies
nothing in particular. The channel refuses to deploy instead.

**Failures happen at deploy, not at the first request.** The store is opened and
the alias resolved while the channel is deploying, so a wrong password, a missing
file, an alias that is not in the store or a store with no private key each fail
with a sentence naming the file and the setting. The certificate being served is
logged with its subject, its issuer and its expiry — and a warning instead when it
expires within thirty days, or has expired already.

### What the channel sees

With TLS on, the source map carries what the transport knows about the caller:

| Key | |
| --- | --- |
| `fhirSecure` | whether this request arrived over TLS |
| `fhirCipherSuite` | the negotiated suite, e.g. `TLS_AES_256_GCM_SHA384` |
| `fhirClientCertSubject` | the client certificate's subject DN — the identity to authorise on |
| `fhirClientCertIssuer` `fhirClientCertSerial` `fhirClientCertNotAfter` | the rest of what a filter might want |

A channel doing mutual TLS authorisation filters on `fhirClientCertSubject`: the
handshake proves the certificate is trusted, and the channel decides whether *that*
subject may do *this*.

### Making a key store

Self-signed, for a test environment:

```bash
keytool -genkeypair -alias fhir -keyalg RSA -keysize 2048 -validity 365 \
  -dname "CN=fhir.example.org, O=Example Health" \
  -ext "SAN=dns:fhir.example.org" \
  -storetype PKCS12 -keystore appdata/fhir/server.p12 -storepass "$PASSWORD"
```

From a real certificate and key (what certbot or a CA gives you):

```bash
openssl pkcs12 -export -name fhir -inkey privkey.pem -in fullchain.pem \
  -out server.p12 -passout "pass:$PASSWORD"
```

And a trust store of the client certificates you accept:

```bash
keytool -importcert -noprompt -alias partner -file partner.crt \
  -storetype PKCS12 -keystore appdata/fhir/clients.p12 -storepass "$PASSWORD"
```

The base URL follows the socket: with TLS on, `request.getScheme()` is `https`, so
the CapabilityStatement's `implementation.url` and every `Location` header say
`https://` without anything else being configured.

## What the channel receives

**Message Content = Body** (the default) hands the channel the request body and puts
everything parsed into the source map:

| Key | |
| --- | --- |
| `fhirVersion` | `R4` / `R5` |
| `fhirInteraction` | `create`, `read`, `search-type`, `transaction`, … |
| `fhirResourceType`, `fhirResourceId`, `fhirVersionId` | from the URL |
| `fhirOperation` | operation name, without the `$` |
| `fhirCompartmentType`, `fhirCompartmentId` | compartment search only |
| `fhirBaseUrl`, `fhirBasePath` | the advertised service base |
| `fhirFormat` | `json` / `xml`, after negotiation |
| `fhirIfMatch`, `fhirIfNoneMatch`, `fhirIfNoneExist`, `fhirIfModifiedSince`, `fhirPrefer` | conditional-interaction headers, lifted out by name |
| `method`, `url`, `parameters`, `headers`, `contextPath` | the HTTP request |
| `remoteAddress`, `remotePort`, `localAddress`, `localPort`, `protocol` | the connection |

`parameters` and `headers` are `Map<String, List<String>>`. Header names arrive exactly as
the client sent them, so `sourceMap.get('headers').get('Accept')` is case-sensitive — the
FHIR-relevant ones are already lifted out above, which covers most of the need.

**Message Content = Request envelope** hands the channel one JSON object instead —
`interaction`, `method`, `url`, `baseUrl`, `format`, `resourceType`, `id`, `versionId`,
`operation`, `parameters`, `headers` and `body` (as a string, never re-serialised) — which
suits a channel whose logic is mostly routing.

## Returning a response

Set the source connector's **Response** to the destination whose output should be returned.
Then:

- a FHIR resource comes back as-is, with `Location`/`ETag`/`Last-Modified` derived from it;
- an empty response becomes 201/204/200 with no body;
- anything that is not a FHIR resource becomes an OperationOutcome carrying it as
  `diagnostics`;
- an errored message becomes 500 with an OperationOutcome built from the error;
- `Prefer: return=minimal` drops the body and `return=OperationOutcome` replaces it.

Response headers come from the connector's own list, or from a channel map variable holding
a map — the same two ways the core HTTP Listener offers.

## Building

```bash
./plugins/oie-fhir-connector/build.sh
cp plugins/oie-fhir-connector/dist/fhir-0.1.0.zip extensions/
docker compose up -d --force-recreate engine
./scripts/oie-check-extensions.sh "FHIR Listener" "FHIR Sender" "FHIR Connector Service Plugin"
```

No local JDK or Maven: it compiles in a container against jars taken straight out of
`oie/engine:4.6.0`, so the extension is always built against exactly the engine it runs on.
`<mirthVersion>` is an exact string match — an extension declaring anything else is refused
and silently not loaded, which is why `build.sh` stamps it from `MIRTH_VERSION`.

The zip contains `source.xml`, `destination.xml`, `plugin.xml`, three jars (shared / server
/ client) and the `webadmin/` half, so one install delivers the engine side, the desktop
Administrator panels and the web console panels together.

## Verified

Against the engine in this repository, with a channel whose source was a FHIR Listener on
`:8082` (R4, base path `/fhir`, resource types limited to `Patient,Observation`, strict
version negotiation) and whose destination was a JavaScript Writer returning resources:

| Request | Result |
| --- | --- |
| `GET /fhir/metadata` | 200, CapabilityStatement with `fhirVersion 4.0.1`, `Content-Type: application/fhir+json; fhirVersion=4.0` |
| `GET /fhir/metadata?_format=xml` | 200, the same statement as FHIR XML |
| `OPTIONS /fhir` | 200, CapabilityStatement |
| `POST /fhir/Patient` | **201**, `Location: …/Patient/created-1/_history/1`, `ETag: W/"1"`, `Last-Modified`, resource body |
| `GET /fhir/Patient/123` | 200, resource, `ETag: W/"3"`, `Last-Modified` from `meta.lastUpdated` |
| `GET /fhir/Patient?name=smith&_count=10` | 200, searchset Bundle |
| `DELETE /fhir/Patient/123` (empty destination response) | **204**, no body |
| `GET /fhir/Practitioner/1` | **404** OperationOutcome `not-supported` — type not served |
| `POST /fhir/Patient/123` | **405** OperationOutcome — method not allowed for that URL |
| `Accept: application/fhir+json; fhirVersion=5.0` | **406** OperationOutcome — endpoint serves 4.0.1 |
| `Accept: text/turtle` | **406** OperationOutcome naming the two formats served |
| `GET /fhir/nonsense/deep/path` | **404** OperationOutcome `not-found` |
| `POST /fhir/Patient/123/$notify` (destination returns plain text) | 200, the text wrapped in an OperationOutcome |
| `X-Forwarded-Proto/Host` set | `Location: https://fhir.example.org/fhir/Patient/created-1/_history/1` |
| `Prefer: return=minimal` | 201, `Location`, `Content-Length: 0` |

And a second channel — an **R5** facade on `:8083` (base path `/gateway`, envelope message
content) whose destination was a **FHIR Sender** posting to the R4 facade above with Basic
authentication, a custom header and `Prefer: return=representation`:

- `POST /gateway/Patient` → **201**, `Content-Type: … fhirVersion=5.0`, `Location`, `ETag`,
  and the resource the R4 facade's channel produced;
- `GET /gateway/metadata` → CapabilityStatement with `fhirVersion 5.0.0`;
- the receiving channel's source map showed the `Authorization`, `X-Test-Header` and
  `Prefer` headers the sender had sent;
- the sender's connector map held `fhirResponseStatusCode`, `fhirResponseLocation`,
  `fhirResponseETag`, `fhirResourceId` and `responseStatusLine`.

Both test channels were deleted afterwards.

### The channel editor

Both panels were opened in the web administrator against the running engine:

- the console logs `[plugins] connector-fhir v0.1.0 registered`, and the connector type
  lists read **FHIR Listener** and **FHIR Sender** rather than "(no web editor)";
- the listener panel renders Listener Settings, FHIR Listener Settings, CapabilityStatement,
  Response and Advanced, with **Response** already defaulted to *Auto-generate (Destinations
  completed)*; switching *GET [base]/metadata* to "Serve the statement below" reveals the
  Custom Statement editor, so the conditional fields work;
- the sender panel, opened on a saved channel, loaded its stored values back: the request
  template in a code editor, the `X-Test-Header` row in the headers table, and the
  interaction, formats and authentication selections.

The desktop Administrator panels are written but have **not** been opened in a running
Swing client.

### TLS

Against the same engine, with a self-signed PKCS12 in the engine's application data
directory and the listener on `:8099`:

| Check | Result |
| --- | --- |
| `openssl s_client` | `TLSv1.3`, `TLS_AES_256_GCM_SHA384`, subject `CN=fhir.local` — the configured alias, not whatever sorted first |
| `GET /fhir/metadata` over HTTPS | 200, CapabilityStatement, `Content-Type: application/fhir+json; fhirVersion=4.0` |
| The advertised base URL | `"url":"https://localhost:8099/fhir"` — the scheme follows the socket with nothing else configured |
| Plain HTTP to the TLS port | connection failed, as it should |
| Client certificates `NEED`, no certificate offered | handshake refused |
| Client certificates `NEED`, certificate offered | 200, and a read interaction dispatched a message |
| That message's source map | `fhirSecure=true`, `fhirCipherSuite=TLS_AES_256_GCM_SHA384`, `fhirClientCertSubject=CN=partner-app,O=Partner Health`, plus issuer, serial and expiry |
| Certificate logged at deploy | `serving CN=fhir.local,O=OIE Test (issued by …), valid until 2027-09-18T13:54:22Z` |

Both deploy-time refusals were exercised on the running engine:

- Client authentication `NEED` with no trust store:
  *Client authentication is set to NEED but no trust store is configured. Without one,
  any certificate signed by a public CA would be accepted.*
- Wrong key store password: the JDK's decryption failure, followed by
  *(check the password and that the file really is a PKCS12 store)*.

## Why there is a service plugin

The engine's `ObjectXMLSerializer` configures XStream with `NoTypePermission`: a class is
deserialisable only if something allowed it. Core connectors are covered by a built-in rule,
and an administrator can extend the list in `mirth.properties` with `xstream.allowtypes`
(in this stack, `_MP_XSTREAM_ALLOWTYPES`).

Relying on that property would make the connector installable but not usable until someone
found the setting, and the failure is nasty: the channel is stored fine, then read back as
an `InvalidChannel` whose only description is "This channel is invalid. Verify all required
extensions are loaded correctly" — pointing at a version mismatch that has not happened.
Nothing is logged at the engine's default level and nothing in the REST API reports it.

So the extension ships a tiny `ServicePlugin` that allows its own two properties classes,
by exact name, at server start — before the engine deploys any channel. This was found the
hard way: the first test channel deployed against this connector came back as exactly that
invalid stub, and a standalone harness against the engine's own serializer produced
`ForbiddenClassException: org.openintegrationengine.connectors.fhir.FhirReceiverProperties`.

## Operating notes

- **Ports.** The listener defaults to `8081`, the channel HTTP port this stack publishes
  (`compose.dev.yaml`, and the proxy overlay's `:8444` → `engine:8081`). Two channels cannot
  share a port; give each facade its own and publish it.
- **Logging.** The connector logs under `org.openintegrationengine.connectors.fhir`. The
  entrypoint's extension logger now covers all of `org.openintegrationengine`, so INFO and
  WARN from it reach the log alongside the other extensions in this repo.
- **Request size.** `Max Request Size` is 0 (unlimited) by default. Behind the nginx
  overlay, `client_max_body_size` applies first.
- **Strict version negotiation** is off by default: a client that asks for a release this
  endpoint does not serve is served anyway. Turn it on for a facade that must not be
  mistaken for another release.
- **Interactions and resource types** are allowlists. Blank means "everything", which is the
  right default for a facade in front of a channel that may route anything; narrowing them
  is how you make a read-only facade, and listing resource types is also what lets the
  generated CapabilityStatement name them.

## Limitations

- **No FHIR validation.** A malformed resource is passed to the channel as it arrived, and
  returned to the client as the channel produced it. Validation belongs in the channel.
- **No version conversion.** An R5 facade in front of an R4 backend is two connectors with
  two version settings, not a translation layer.
- **No JSON ↔ XML conversion**, for the same reason — the media type describes what the
  body actually is.
- **No OAuth2 client-credentials flow in the sender.** Basic and bearer are built in; a
  token fetched by the channel goes in the Bearer Token field as `${variable}`.
- **The Authentication section on the listener panel does nothing.** It is contributed by
  the engine's HTTP Authentication plugin, which offers itself to listener connectors
  generally; this connector does not consult those plugin properties, so anything set there
  is stored and ignored. Put authentication in front of the facade (the proxy overlay), or
  ask for httpauth support to be wired in.
- **The desktop Administrator panels are functional, not pixel-perfect.** They carry every
  property the web console's panels do, with headers and parameters as `Name: value` per
  line instead of an editable table.
